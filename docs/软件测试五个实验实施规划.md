## 1. 实验一：测试管理工具（TestLink / Testcenter）

### 1.1 设计思路
- 目标：在主干上跑通一次**最小闭环**——需求→用例→计划→执行→缺陷，能追溯、能出数，不做全量覆盖。
- 选型：**TestLink 1.9.20 本地部署**（免安装、独立库 `testlink`，不碰 `j2eedb`），不用 Testcenter。
- **规模刻意压缩**：10 条需求、20 条用例、1 个测试计划、1 轮执行。收敛范围的依据写进报告：主干预选为"到货→销售出库"这一条贯通链路，其余模块显式列为范围外——**收敛是实验一的能力项，不是偷工**。
- 用例用 **XML 批量导入**，不在界面里逐条敲。

### 1.2 实现过程（5 步，半天）
1. 环境：PHP 7.4.33 + 独立 MySQL 实例（实际使用 3309、`testlink-mysqldata`；3308 已有 MES 数据，保留原状）+ TestLink 1.9.20，`php -S 127.0.0.1:8085`；建产品 `温衡智造 MES 实验一`，2 个账号（admin、tester）。安装与执行说明见 `docs/lab1/README.md`。
2. 需求：10 条，按 REQ 原始编号录入。
3. 用例：20 条 = 5 个套件 × 4 条（主数据/仓储/生产/质量/销售），正例 12、异常 8；写一份 XML 一次导入。
4. 计划：建 1 个测试计划挂 20 条用例，1 轮执行；失败项当场复测，不另建 R2。
5. 执行与缺陷：浏览器按用例跑，记通过、失败或阻塞；有多少真实缺陷就记录多少并写复现步骤，不为满足 3～5 条而造记录。准备阶段全部标为未执行。

### 1.3 系统应用（证据：3 图 + 4 表）
省截图的关键是**用表格承载清单**：20 条用例放进表格，就不需要 20 张截图。

三张图（每张都得有用）：
- 图 1-1 需求树与对应用例（一屏同时体现需求与用例，省一张）
- 图 1-2 测试计划执行结果汇总
- 图 1-3 缺陷列表 + 1 条展开

四张表：
- 表 1-1 需求覆盖矩阵（10 行）
- 表 1-2 用例清单（20 行：编号 / 需求 / 标题 / 预期 / 结果）
- 表 1-3 执行结果统计
- 表 1-4 缺陷清单（按真实发现数量填写；准备阶段留空）

### 1.4 显式不做（写进报告的边界声明）
不做 R2 独立计划、不做设备/排班/系统管理模块、不做邮件通知与缺陷系统集成、不做报表模板定制、不导出 CSV/HTML。

### 1.5 风险
- 本机旧版实验固定使用 PHP 7.4.33；数据库账号采用 `mysql_native_password` 兼容安装器，但不能笼统声称 PHP 7.4.33 不支持 `caching_sha2_password`。网页/XML 保持 UTF-8，数据库、表和连接统一 utf8mb4；实际部署使用独立 3309。
- 执行记录与缺陷必须真实，否则一眼假。

## 2. 实验二：单元测试工具（JUnit + Mockito + JaCoCo）

### 2.1 设计思路
- 目标：把主干单元测试从"能跑"推进到"可度量 + 有门禁"。现状 37 个测试类、**从未度量覆盖率**，这正是报告里最好的切入点。
- 分层策略：service 层用纯 Mockito（不起 Spring 容器，跑得快、可离线）→ 覆盖率门槛设在能达成的区间（整体行覆盖目标 35%～45%，被选中的 6 个核心 service 分支覆盖 ≥60%），不要写"80%"这种交不出来的数字。
- 不测什么：Mapper XML 的动态 SQL（属实验四接口层）、Controller 参数绑定（框架行为）、`ktg-generator`/`ktg-quartz`（若依原生，非自研）。

### 2.2 实现过程
1. **构建改造**（写进报告"实现过程"的核心）：
   - 根 `pom.xml` 增加 `jacoco-maven-plugin` **0.8.8**（JDK8 兼容上限），绑定 `prepare-agent` + `report` + `report-aggregate`（父工程聚合 8 个子模块）。
   - `ktg-mes/pom.xml` 显式声明 `mockito-core`（当前靠 `spring-boot-starter-test` 传递 3.9.0，显式化便于写版本）；必要时加 `mockito-inline` 以 mock final 类。
   - JaCoCo `check` 规则第一轮只 `warn` 不 `haltOnFailure`，避免把自己卡死；报告中说明这是"渐进式门禁"。
2. **选点**（主干里分支多、业务价值高的类）：

| 被测类 | 覆盖的业务规则 | 建议新增用例数 |
|---|---|---|
| `IssueAutoPickService` | 整单自动拣货 FIFO 拆批、库存不足、跨库位 | 10 |
| `ProFeedbackBatchExecution` | 报工批次范围校验、数量合计不等 | 10 |
| `FormLinkagePolicy` + `*LinkageService`（7 个） | 单据上下游状态机、非法跳转 | 16 |
| `DvCheckRecordPcGuard` | PC 端点检防重复提交 | 8 |
| `FaceTemplateTest`（已有，补） | 人脸 1:1 比对阈值边界 | 6 |
| `RqcConclusionConsistency` / `RqcReturnGuard` | 退货检验结论一致性 | 10 |

3. 写法沿用主干已有风格（`@Before` 手工构造 + `mock()` + `ArgumentCaptor`，见 `IssueAutoPickServiceTest`），保证 reviewer 看着一致。
4. 执行与取数：`mvn -B -pl ktg-admin -am test` → `mvn jacoco:report-aggregate` → 打开 `ktg-mes/target/site/jacoco/index.html`。

### 2.3 系统应用（证据）
- `Tests run: N, Failures: 0, Errors: 0, Skipped: 0` 的控制台汇总（改造前后各一次）
- JaCoCo 总览页（行/分支覆盖百分比）+ 2 个核心类的红绿明细页
- 一个 Mockito `verify(...)` + `ArgumentCaptor` 的用例代码片段（说明测的是行为不是实现）
- 覆盖率提升对比表（模块 × 改造前/后）

### 2.4 风险
- `JAVA_HOME` 若仍是 JDK 21，`mvn test` 直接失败 —— 这是第一步就要写进报告的环境校验。
- 首次 `mvn` 需联网拉 jacoco 依赖，注意本地仓库。
- 覆盖率低不代表质量差，报告里要写清"分母是 1238 个类中含若依原生代码"的统计口径。

## 3. 实验三：静态测试工具（Alibaba Java Coding Guidelines、SpotBugs）

### 3.1 设计思路
- 目标：对主干做**可复现**的静态扫描，产出问题清单、按规则分类、定向修复、复扫对比。
- 双轨：
  - **IDE 轨**（报告要的"工具使用"）：IDEA 装 *Alibaba Java Coding Guidelines* 2.1.x + *SpotBugs* 插件，扫描自研模块，导出报告。
  - **CI 轨**（保证可复现，推荐）：Maven 挂 `p3c-pmd`（阿里 PMD 规则集，headless）+ `spotbugs-maven-plugin` **4.7.3.6**（4.8 起要求 JDK11），产物 `target/pmd.xml`、`target/cpd.xml`、`target/spotbugsXml.xml`。
  - 报告里写"为什么两条轨都做"：IDE 出截图，Maven 出可版本化的数字。
- 扫描范围与**噪声口径**（这是实验三的关键判断）：
  - 扫 `com.ktg.mes.**`、`com.ktg.system.**`、`com.ktg.framework.**`
  - 排除 `ktg-generator`、`ktg-quartz`（若依原生）与 `target/`
  - 若不排除，原生代码违规占比过半，修复率会被稀释，结论不可信。

### 3.2 实现过程
1. 建立**扫描前基线**：全量扫描一次，记录各严重级别条数，按模块拆分。
2. 分类统计：阿里规则 Blocker/Critical/Major × 规则名（空指针风险、资源未关闭、日志字符串拼接、集合未指定初始容量、命名规范、魔法值、事务边界）；SpotBugs High/Medium × 缺陷模式（NP_NULL、DM_DEFAULT_ENCODING、EI_EXPOSE_REP、SQL 拼接、`SimpleDateFormat` 静态复用）。
3. 修复策略（写清取舍，体现质量判断）：
   - 必修：所有 Blocker/Critical + SpotBugs High
   - 抽样修：Major 中挑 20 条高价值的
   - 不修并说明：历史代码/与上游若依保持一致的部分，列入"未修复说明"，附理由
4. 复扫：`mvn pmd:pmd spotbugs:spotbugs`，出"扫描后"数字，算修复率。
5. 挑 5 组 Before/After（建议）：
   - `new BigDecimal(double)` → `BigDecimal.valueOf`
   - `e.printStackTrace()` → `log.error(..., e)`
   - 日志 `log.info("x"+var)` → `log.info("x{}", var)`
   - 静态 `SimpleDateFormat` → `DateTimeFormatter`
   - `HashMap` 未指定容量 / `Collections.emptyList()` 返回可变引用（EI_EXPOSE_REP）

### 3.3 系统应用（证据）
- 扫描前后条数对比表（模块 × 严重级别）
- 规则命中分布图（Top 10 规则条形图）
- SpotBugs 报告的 High 项列表截图
- 5 组 Before/After 代码对照（带文件路径和行号）
- 修复率与未修复说明

### 3.4 风险
- 全量扫描可能上千条 → 报告必须"收敛"，按模块给基线、只承诺增量清零，否则写不完也说不清。
- `p3c-pmd` 与 PMD 版本绑定（`p3c-pmd 2.1.1` 对应 PMD 6.x），和 JDK8/Spring Boot 2.5 组合要先试通再写死版本。

## 4. 实验四：接口测试工具（Postman）

### 4.1 设计思路
- 起点很好：`ktg-mes.postman_collection.json` 已有 **7 个文件夹、38 个请求**，集合级已配 `bearer {{token}}`，环境文件 `{{baseUrl}}`。但**一个断言都没有**（无 `pm.test`）。这就是"设计思路"的立论：从"能点通"升级到"能自动判定"。
- 目标：40～60 个请求全部带断言，Token 自动续期，Newman 一键出 HTML 报告，可进回归。
- 覆盖维度：正向 CRUD、认证鉴权、参数校验（负数/缺参/分页边界）、业务联动（跨接口数据依赖）。

### 4.2 实现过程
1. **认证链路（集合级）**：`GET /captchaImage` 取 `uuid` → 开发环境关验证码或按配置取码 → `POST /login` → `pm.environment.set('token', json.token)` → 所有请求走 `Authorization: Bearer {{token}}`；再加一个"token 失效后自动重登"的 collection pre-request 逻辑。
2. **断言模板**（统一三层）：
   ```js
   pm.test('HTTP 200', () => pm.response.to.have.status(200));
   pm.test('业务码 200', () => pm.expect(pm.response.json().code).to.eql(200));
   pm.test('分页结构完整', () => {
     const d = pm.response.json().data;
     pm.expect(d).to.have.property('total').that.is.a('number');
     pm.expect(d.rows).to.be.an('array');
   });
   ```
3. **业务变量链**（新建文件夹 `07 业务联动链`）：新建物料 → 存 `itemId` → 查详情 → 建 BOM 引用 `itemId` → 建工单 → 排产 → 报工 → IPQC → 清理。等于用接口把实验一那条链路再跑一遍，两份报告互相印证。
4. **负例与鉴权**：
   - 无 token → 期望 401
   - `operator` 账号调删除类接口 → 期望 403
   - 缺必填字段 → 期望业务码 500/自定义 msg
   - 分页 `pageSize=0` 与 `pageSize=100000` → 期望被规范化或明确报错
5. **数据驱动**：`postman/data/items.csv`（10 组物料编码），Runner 迭代或用 Newman `--iteration-data`。
6. **Newman 批跑**：
   ```
   newman run ktg-mes.postman_collection.json -e ktg-mes.postman_environment.json \
     -r cli,htmlextra --reporter-htmlextra-export evidence/lab4/newman-report.html
   ```

### 4.3 系统应用（证据）
- Postman Collection Runner 结果页（总请求数 / 断言数 / 通过失败计数）
- Newman HTML 报告首页 + 1 个失败用例展开图
- 接口清单表（模块、方法、路径、断言数、结果）——40 行以上的表
- 断言代码片段 + 变量链截图

### 4.4 风险
- 写操作污染数据 → 固定连 `j2eedb_it`，每个文件夹末尾放清理请求，链式请求用固定前缀 `PFX-LAB4-` 便于删。
- 验证码：`GET /captchaImage` 返回的校验码无法 OCR → 在 `application.yml` 用 `captchaEnabled=false` 的测试 profile，报告里说明这是测试环境配置，不等于生产。
- 端口：默认 8080，演示库脚本走 8081，环境文件里 `baseUrl` 要写清用哪个。

## 5. 实验五：性能测试工具（JMeter + Badboy）

### 5.1 设计思路
- 目标：3 条核心链路做阶梯加压，出 TPS / 响应时间 / 错误率 + 资源曲线，定位 1～2 个真实瓶颈并给优化建议，再做优化前后对比。
- 场景选型（覆盖读、写、统计三类）：
  1. **并发登录 + 首页工作台**（含 4 个图表接口）：验 JWT/Redis 与统计查询
  2. **生产工单列表 + 详情**（分页 + 多表 join）：读多场景
  3. **报工提交**（写事务 + 库存/批次联动）：写场景，验事务与锁
- Badboy 定位要写实：它停留在 IE 内核（2010 年后未更新），在 Win10/11 上通常装不上或抓不到 HTTPS。所以流程写成"**用 Badboy 录制 → 导出 .jmx → 导入 JMeter 修正关联**"，并同时准备 fallback：JMeter 自带 *HTTP(S) Test Script Recorder* 代理录制，或把实验四的 Postman 集合转 JMeter。**这个取舍本身就是报告里的质量判断，不要假装 Badboy 顺利可用。**

### 5.2 实现过程
1. 录制：Badboy 录场景 1 → `.jmx`；场景 2、3 用 JMeter 代理录制补全。
2. JMeter 加工：
   - `CSV Data Set Config`：10～100 个账号（用 README 里 8 个角色账号扩出测试账号）
   - `JSON Extractor` 提取 `token` 做关联，`Response Assertion` 校验 `"code":200`
   - `jp@gc Stepping Thread Group`：10→50→100→200 阶梯，每档保持 5 min
   - `Constant Throughput Timer` 控 TPS、`Synchronizing Timer` 造并发峰值
   - `jp@gc PerfMon Metrics Collector` 采 CPU/内存（需 ServerAgent）
3. 执行（非 GUI）：
   ```
   jmeter -n -t plan.jmx -l result.jtl -e -o evidence/lab5/jmeter-report
   ```
4. 监控面：Druid 监控页 `/druid`（连接池活跃数/等待）、MySQL `SHOW PROCESSLIST` + 慢查询日志、Redis info、`top`。
5. 定位与优化（至少给 2 条）：
   - 典型嫌疑：列表查询无索引 → `EXPLAIN` 出 `ALL` 全表扫 → 建索引后复压
   - 图表接口一次拉 30 天明细 → 改聚合/加 Redis 缓存 → 复压
6. 复压对比，出优化前后同口径表格。

- JMeter HTML Dashboard 首页（TPS / RT / 错误率三张曲线）

### 5.4 风险（报告里要主动声明）
- JMeter 与被测应用同机 → 互相抢 CPU，**结论按相对趋势，不按绝对容量**。
- MySQL 默认参数未调优、Redis 单机 → 一并声明为"环境限制"。
- 单机施压线程上限约 500～800（受 JMeter 自身限制），需要更高并发才考虑分布式。
