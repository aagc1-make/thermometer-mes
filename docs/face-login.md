# 人脸登录（浏览器本地 1:1 比对）

## 结论与定位

在现有账号密码登录之外，增加“账号 + 人脸”的第二条登录路径。它适合演示和内部车间终端：

- 人脸只作为**登录方式之一**，不替代密码；密码登录、验证码登录保持原样。
- 采用 **1:1 比对**（先输入账号，再比对该账号已录入的人脸），不做 1:N 刷脸检索，避免共用终端上误识别到其他人。
- 人脸检测、活体判断、特征提取全部在浏览器完成，服务端只接收 128 维特征并做距离比对，不接触照片和视频。

## 使用

1. 先用密码登录，进入“个人中心 → 人脸登录”。
2. 点“录入人脸”，输入当前登录密码，勾选授权说明，点“开始采集”。
3. 正对摄像头，按提示眨一次眼或轻轻左右转头，采集 3 帧后自动完成。
4. 退出后回到登录页，切到“人脸登录”，输入账号，点“开始人脸识别”即可登录。
5. 需要停用时，在个人中心点“解绑人脸”，输入密码后特征立即删除。

超过 5 次比对失败会在 10 分钟内拒绝该账号的人脸登录（可用密码登录），失败次数记录在 Redis，窗口和阈值可配置。

## 数据流

```
浏览器                                   服务端
摄像头 → TinyFaceDetector 检测人脸
      → 68 点关键点：眨眼/转头活体
      → FaceRecognitionNet 128 维特征
      → 多帧平均 → POST /faceLogin
                                    查 sys_user_face → 欧氏距离 ≤ 阈值
                                    → 通过：签发同款 JWT / 失败：统一提示 + 审计
```

- 关键点：`face-api.js 0.22.2`（`public/face-api/face-api.min.js`），模型：`tiny_face_detector`、`face_landmark_68`、`face_recognition`，共约 6.8MB，放在 `public/face-api/models`，首次使用时加载。
- 活体：双眼平均 EAR 低于闭眼阈值再恢复（眨眼），或鼻尖相对人脸框的横向位移超过 12%（转头）；两条满足其一即通过。
- 阈值：欧氏距离 `0.55`；同一人通常 0.3~0.5，不同人通常大于 0.6。前端 `FACE_THRESHOLD` 与后端 `mes.face.threshold` 必须一致，单元测试会校验。

## 安全与隐私设计

| 关注点 | 处理 |
|---|---|
| 生物特征存储 | 只存 128 维特征（`sys_user_face.descriptor`），不存照片；解绑即删行；备注记录授权用途 |
| 账号枚举 | 未录入、比对失败、账号不存在统一返回“账号未录入人脸或人脸不匹配” |
| 暴力试探 | 账号维度 5 次 / 10 分钟；IP 维度 20 次 / 10 分钟（避免共享出口误伤所有人）。计数在 Redis，登录成功清零；不存在的账号只计入 IP 维度，避免任意用户名撑大缓存 |
| 会话劫持后改绑 | 录入/解绑都要求重新输入登录密码，并限制密码尝试次数 |
| 知情同意 | 录入前必须勾选授权说明，服务端校验 `agree=true` 才写入 |
| 审计 | 成功/失败均写 `sys_logininfor`，失败原因只记服务端（如 `NOT_MATCHED，distance=4.4879`） |
| 传输 | 只传特征；生产环境必须 HTTPS，否则特征与令牌可被截获 |
| 权限 | `/faceLogin` 匿名但限流；`/system/user/face/**` 需登录，只能操作本人模板 |

**能力边界**：当前活体是“眨眼/转头”级别的轻量检测，能挡住静态照片，但挡不住提前录制的眨眼视频或深度伪造。对安全要求更高的场景，应改用 WebAuthn（Windows Hello / Face ID）或带活体检测的云端人脸核身服务。特征目前明文存库，生产环境建议再加字段级加密与密钥托管。

## 配置

`backend/ktg-mes/ktg-admin/src/main/resources/application.yml`：

```yaml
mes:
  face:
    enabled: true        # 关闭后登录与录入接口直接拒绝
    threshold: 0.55      # 欧氏距离阈值，调大更宽松
    max-fail: 5          # 连续失败次数上限
    fail-window: 600     # 失败计数窗口（秒）
```

建表脚本：`sql/face_login.sql`（`sys_user_face`）。

前端资源：`ktg-mes-ui/public/face-api/`；构建后随 `dist/face-api` 发布。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/faceLogin` | 匿名，`{username, descriptor}`，成功返回 `{token}` |
| GET | `/system/user/face/status` | 当前账号是否已录入 |
| POST | `/system/user/face/enroll` | `{password, descriptor, samples, quality, agree}`，录入/更新 |
| DELETE | `/system/user/face` | `{password}`，解绑并删除特征 |

## 验证记录（2026-11-01）

- 离线单测：`node scripts/run-unit-tests.mjs` 共 159 项通过，其中新增 9 项覆盖特征校验、阈值、多帧平均、EAR、眨眼/转头活体、前后端阈值一致性。
- 后端 Java 单测：`FaceTemplateTest` 6 项通过（解析、维度、常量向量、距离、平均）。
- 后端全链路脚本：验证码登录 → 录入 → 状态 → 同特征登录 → 令牌访问 `/getInfo` → 异特征拒绝 → 常量特征拒绝 → 不存在账号统一提示 → 密码错误解绑被拒 → 正确解绑 → 解绑后不可登录 → 连续失败触发限流 → 清理计数，全部通过。
- 浏览器验证（Chrome headless + 真实人像）：登录页人脸 Tab 与按钮可见；摄像头打开、模型加载、假摄像头下给出“没有检测到人脸/眨眼提示”；取消后释放摄像头；页面内从真实人像提取 128 维特征（score 0.907）；经代理录入成功；人脸登录拿到令牌；调用登录页真实方法后进入 `/index`；个人中心显示“已录入人脸”；验证后清理模板。
- 登录审计可在 `sys_logininfor` 查询到“人脸登录成功/失败”记录。

## 已知限制

- 仅支持具备摄像头且为安全上下文（HTTPS / localhost）的浏览器；不提供降级到其他设备的方案。
- 模型首次加载约 1~3 秒（本地资源），低端机特征提取可能更慢；界面会显示加载状态，超时 30 秒可重试。
- 用户更换外观（眼镜、胡须、大幅妆容）或光线过暗时可能比对失败，建议重新录入。
- 模板与账号绑定，不跨账号复用；不提供管理员代录，避免代替他人授权。
- 车间共用终端建议保留密码登录作为兜底，并在制度上要求“人走锁定/退出”。
