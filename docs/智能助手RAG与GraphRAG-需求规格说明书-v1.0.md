## 1 引言

### 1.1 编写目的

定义 MES 智能助手在阶段2 要达成的能力边界与验收口径。本文面向：指导教师（评审范围与现场验收）、开发人员（实现边界）、测试人员（用例来源）。

### 1.2 项目背景与现状

阶段1 已交付能力（本文的改造起点）：

| 现有能力 | 实现现状 | 本阶段差距 |
| --- | --- | --- |
| 模型接入 | DeepSeek-chat 主 + GLM-4-Flash 兜底，3s 超时，密钥走环境变量；**仅用于意图解析与片段分析** | 无生成式问答；无本地模型通道；模型不参与数据访问决策 |
| 意图解析 | 模型输出 JSON 槽位（metric/timeText/category…），由**前端规则引擎**执行查询 | 模型只"理解"不"执行"；槽位固定，新增场景要改代码 |
| 数据访问 | 前端按槽位调用既有接口（库存、工单、检验…），规则兜底 | 模型无法自主选择工具、无法多步串联 |
| 知识库 | 浏览器 IndexedDB 按账号隔离 + 前端关键词检索，支持 5 类格式与版本管理 | 无向量化、无服务端存储、无图谱、无部门级共享 |
| 业务问答 | 规则引擎读真实单据回答库存/检验类问题 | 与文档知识割裂，未融合 |
| 后端接口 | `/mes/ai/intent`、`/mes/ai/analysis`、`/mes/ai/status` | 无知识库/向量/图/工具调用相关接口 |

**本阶段目标**：把「模型解析 → 前端写死规则查数 → 模板回答」升级为「**模型自主规划 → 按需检索文档/图谱/业务数据 → 生成带溯源的回答**」，同时满足部门级隔离与图谱可视化两项硬性要求。

### 1.3 术语与缩略语

| 术语 | 含义 |
| --- | --- |
| RAG | 检索增强生成：向量/关键词召回文档片段后交给模型作答 |
| GraphRAG | 以知识图谱为检索源的 RAG：先实体链接与子图扩展，再交给模型作答 |
| 工具调用（Tool/Function Calling） | 模型输出结构化的工具名与参数，由后端执行并把结果回填给模型 |
| 三路召回 | 向量库（文档）、图数据库（关系）、业务数据库（实时数据）三种知识源 |
| 部门库 | 以部门为隔离单位的隐私知识库，本项目的租户粒度 |
| 分块（Chunk） | 文档的检索单元，带文档/版本/页码元数据 |
| 本体（Ontology） | 允许的实体与关系类型白名单，见附录 B |
| 金标集 | 人工标注的「问题—应命中片段/应查到数据」评测集 |

## 2 总体描述

### 2.1 产品定位与边界

本模块是 MES 内部的**私有化智能问答子系统**：模型在同一个会话里既能查文档、又能查图谱、还能查实时业务数据，并给出带溯源的答案。

**本阶段包含**

1. 模型双通道接入（外部 API + 本地 GPU 部署）与运行时降级；
2. 部门级隔离的隐私知识库与文档全生命周期；
3. 文档 → 向量库的实时嵌入与更新；
4. 文档 → 图数据库的转换与实时更新（按文档分类选择性建图）；
5. **大模型工具调用**：解析问题 → 选工具 → 查 MES 数据 → 生成回答；
6. RAG / GraphRAG / 数据问答三种能力的路由与融合；
7. 知识图谱前端可视化；
8. Dify 编排（必须）与创新点落地。

**本阶段不包含（防蔓延）**

1. 不做模型微调训练；
2. **工具调用一律只读**：模型不得直接写库、不得改单据；需要建单时沿用阶段1「意图 → 表单 → 用户确认提交」的既有流程；
3. 不做公网多租户 SaaS，部署形态为内网单实例；
4. 不做移动端/小程序端；
5. 不做扫描件 OCR；
6. **不迁移阶段1 浏览器本地知识库数据**（用户自行重新上传）。

### 2.2 用户角色与权限

| 角色 | 说明 | 关键权限 |
| --- | --- | --- |
| 部门成员（USER） | 业务人员 | 使用本部门的库问答；查看图谱（限本部门）；使用数据问答 |
| 库维护者（OWNER） | 部门内的知识库负责人 | 上传/更新/删除本部门文档；触发重建索引 |
| 系统管理员（ADMIN） | 系统管理员 | 创建部门库；配置模型与向量库；配置工具白名单；查看全量审计 |

- **隔离单位 = 部门**。一个部门一个库（可扩展为多库，权限按库授）。
- 用户归属部门取自现有 `sys_user.dept_id`，不新增账号体系。
- 跨部门访问一律拒绝；管理员**也不提供跨部门检索**，只能逐个部门查看。

### 2.3 运行环境与技术形态

| 项 | 要求 |
| --- | --- |
| 部署 | 内网单服务器，Docker Compose 拉起应用、MySQL、Qdrant、Neo4j、本地模型服务 |
| GPU | **NVIDIA GeForce RTX 4060 Laptop，8188 MiB（8 GB）**，已实测确认；用于本地对话模型推理，嵌入与重排走 CPU 以保留显存 |
| 模型通道 A | 外部大模型 API（OpenAI 兼容协议），默认 DeepSeek-chat，可从配置切换 |
| 模型通道 B | 本地部署：**Qwen2.5-7B-Instruct（Q4_K_M 量化，主力档）+ Qwen2.5-3B-Instruct（快档）**，Ollama 或 llama.cpp 承载；嵌入 bge-m3、重排 bge-reranker-v2-m3 均走 CPU |
| 通道策略 | 默认「本地优先、外部兜底」；两者均不可用时降级为仅检索 |
| 前端 | 现有 Vue 2 + Element UI，Chrome/Edge 最新，最小 1366×768 |
| 后端 | 现有 Spring Boot，沿用 RuoYi 权限与审计 |
| 数据出网 | 使用外部通道时，只发送「当前问题 + 命中片段 + 工具返回的聚合结果」，不发送原文全量；管理员可关闭外部通道 |

**显存预算（8 GB 卡）**

| 组件 | 显存占用 | 部署建议 |
| --- | --- | --- |
| Qwen2.5-7B-Instruct Q4_K_M | ≈ 4.7 GB | 主力档；上下文控制在 2k tokens 以内，给 KV cache 留 2 GB 余量 |
| Qwen2.5-3B-Instruct Q4 | ≈ 2.0 GB | 快档；与 7B 二选一加载，不并存 |
| bge-m3 嵌入 | 0（CPU） | 建库与查询时的编码在 CPU 上完成，单次 ≤ 300 ms |
| bge-reranker-v2-m3 | 0（CPU） | 仅对 Top20 重排，延迟 < 200 ms |
| 合计峰值 | ≈ 5.5 GB | 余量 ~2.5 GB，留出浏览器与别的进程 |

> 结论：8 GB 卡上**不要同时加载 7B 与 14B**，也不要把嵌入模型放 GPU；这是"本地能跑起来"和"本地卡死"的分界线。

## 3 功能需求

### 3.1 模型接入与运行时（FR-M）

| 编号 | 名称 | 优先级 |
| --- | --- | --- |
| FR-M-01 | 本地 GPU 模型接入 | P0 |
| FR-M-02 | 外部大模型 API 接入 | P0 |
| FR-M-03 | 双通道切换、自检与降级 | P0 |
| FR-M-04 | 生成参数与提示词配置 | P1 |
| FR-M-05 | 流式输出与中断 | P1 |
| FR-M-06 | 嵌入模型与重排模型接入 | P0 |

**FR-M-01** 管理员可配置本地推理服务地址、模型标识、上下文长度、并发上限；保存后即时生效。验收：切换到本地模型提问，回答页显示「本地 Qwen2.5-7B」且延迟达标。

**FR-M-02** 支持 OpenAI 兼容协议，可配 base_url、apiKey、模型名、超时、重试；密钥只从环境变量/配置中心读取，不落业务表明文、不出现于前端产物。

**FR-M-03** 提供 `/mes/ai/status` 健康状态（本地、外部、向量库、图库、Dify 五项）。降级顺序：本地 → 外部 → 仅检索。任何一级不可用都要在界面明示，不得静默失败。

**FR-M-06** 嵌入模型可配（本地 bge-m3 或 API embedding），重排模型（bge-reranker-v2-m3）可开关；更换嵌入模型时必须支持全库重建索引。

### 3.2 隐私知识库与部门级隔离（FR-K）

| 编号 | 名称 | 优先级 |
| --- | --- | --- |
| FR-K-01 | 部门库创建 | P0 |
| FR-K-02 | 存储侧隔离 | P0 |
| FR-K-03 | 检索侧隔离 | P0 |
| FR-K-04 | 成员与角色 | P1 |
| FR-K-05 | 配额与容量 | P2 |

**FR-K-01** 管理员按部门创建知识库，与 `sys_dept` 关联；部门成员登录后自动可见本部门库，无需手工授权。

**FR-K-02** 文档、分块、向量、图节点均携带 `dept_id` + `library_id`；所有查询语句必须带该条件，禁止无过滤的全量返回。

**FR-K-03 检索侧隔离**：向量检索、图谱检索、工具调用三处均在**语句层面**附加部门过滤，而非检索后过滤。验收见 7.4 越权用例，要求泄露条数 = 0 且写审计。

**FR-K-04** 成员分只读/维护/管理三档，变更下一次请求即生效。

**FR-K-05** 单库配额：文档 ≤ 500、总字符 ≤ 2000 万、单文件 ≤ 50 MB。

### 3.3 大模型工具调用与业务数据问答（FR-A）★本次新增核心

> 需求来源：评审反馈「模型解析问题之后能够访问数据，然后生成对话回答」。这是本阶段与阶段1 最大的能力差异。

| 编号 | 名称 | 优先级 |
| --- | --- | --- |
| FR-A-01 | 只读工具注册表 | P0 |
| FR-A-02 | 模型驱动的工具调用 | P0 |
| FR-A-03 | 参数校验与只读沙箱 | P0 |
| FR-A-04 | 结果集裁剪 | P0 |
| FR-A-05 | 计算后置（不把算数交给模型） | P0 |
| FR-A-06 | 多步编排与终止条件 | P1 |
| FR-A-07 | 权限继承与审计 | P0 |
| FR-A-08 | 数据来源标注 | P0 |
| FR-A-09 | 失败兜底到规则引擎 | P0 |

**FR-A-01 只读工具注册表**
以声明式方式注册可用工具，每个工具包含：工具名、中文描述（模型据此选工具）、参数 JSON Schema（类型/必填/枚举/范围）、后端实现（复用现有 Service）、是否只读、所需权限点。首批至少覆盖：库存查询、出入库流水、工单查询与进度、BOM 展开、检验记录查询、安全库存预警、物料信息查询。工具清单在「系统设置 → AI 工具」中可查看，**不提供新增写工具的能力**。

**FR-A-02 模型驱动的工具调用**
用户提问后，由模型自主决定：直接回答 / 调用一个或多个工具 / 请求文档检索。模型输出必须符合 `tool_calls` 结构，后端解析后执行。验收：问「10 月份测温显示电控预装件的库存是多少」，系统调用库存工具并返回准确数字与表格，回答中不出现未经验证的推测值。

**FR-A-03 参数校验与只读沙箱**
工具入参必须按 Schema 校验（类型、枚举、日期格式、ID 存在性）；拒绝超范围参数（如 `pageSize>200`、日期跨度过大）并回告模型重新组织。**禁止模型生成并执行 SQL**；所有数据访问通过预定义工具走 Service 层，SQL 由后端参数化拼装。

**FR-A-04 结果集裁剪**
单次工具返回行数 ≤ 200（可配），超出时返回聚合摘要 + "共 N 条，已折叠"；单轮最多 3 次工具调用，超过即终止并要求用户缩小范围。写入模型的上下文总量 ≤ 8k 字符。

**FR-A-05 计算后置**
合计、占比、同比、平均等**由后端 SQL 完成**，模型只做文字表述；回答中出现任何数值必须有对应工具返回值支撑。验收：构造 50 行明细让模型"算合计"，回答中的合计值必须与后端聚合结果完全一致（0 容差）。

**FR-A-06 多步编排**
支持"先查工单 → 再查该工单的检验记录"这类串联（最多 3 步）；每一步的中间结果记入会话上下文；任一步失败即返回已获得的部分结果并说明原因。

**FR-A-07 权限继承与审计**
工具执行继承当前登录用户的角色与部门数据权限；越权请求返回 403 并记审计。审计字段：用户、工具名、脱敏参数、返回行数、耗时、是否越权。

**FR-A-08 数据来源标注**
回答末尾固定输出「数据来源」区块：命中的表/接口、数据条数、查询时间、以及本次是否使用了文档/图谱。示例：`数据来源：库存表 3 条（2026-11-20 15:04:12）；文档引用 [1][2]`。

**FR-A-09 兜底**
模型未输出合法工具调用、或工具连续失败时，回落到阶段1 的规则引擎（意图槽位 + 固定查询），保证"模型挂了也能答"。验收：禁用模型后重复 FR-A-02 的提问，仍能返回正确的库存数字，并标注"规则引擎兜底"。

### 3.4 文档全生命周期管理（FR-D）

| 编号 | 名称 | 优先级 |
| --- | --- | --- |
| FR-D-01 | 多类型上传 | P0 |
| FR-D-02 | 原文下载 | P0 |
| FR-D-03 | 版本更新与增量重建 | P0 |
| FR-D-04 | 删除与级联清理 | P0 |
| FR-D-05 | 列表、筛选与分页 | P1 |
| FR-D-06 | 解析失败与扫描件提示 | P1 |
| FR-D-07 | 处理进度可见 | P1 |
| FR-D-08 | 操作审计 | P1 |

**FR-D-01** 支持 PDF、DOCX、TXT、MD、CSV、XLSX、HTML（PPTX 为 P2）；扫描件不做 OCR，明确提示。
**FR-D-02** 有权限用户可下载原文，记审计。
**FR-D-03** 同名同分类为同一文档；新版本自动停用旧版并**触发向量与图谱增量重建**。验收：V1 检索命中 → 上传 V2 改段落后，命中内容为 V2，V1 分块不再出现。
**FR-D-04** 删除时同步清理分块、向量、图谱节点与边；历史会话中的引用保留快照并标注"该版本已删除"。
**FR-D-07** 四阶段进度：解析 → 向量化 → 图谱抽取 → 完成；失败可查看原因并重试。

**FR-F-01** 对话界面提供 `自动 / 仅文档(RAG) / 图谱(GraphRAG) / 数据问答(工具)` 四档，满足任务-3「提供可选界面」的要求。
**FR-F-02** 自动路由规则（可配置）：出现关系型词（依赖、用在、关联、上下游）或命中已知实体 → 走向量 + 图；出现明确指标词（库存、数量、进度、检验结果）→ 走工具；定义/规范类 → 走向量；混合问题 → 工具 + 文档组合。

### 3.10 Dify 编排与创新点（FR-W）★必须项

| 编号 | 名称 | 优先级 |
| --- | --- | --- |
| FR-W-01 | Dify 工作流编排 | P0 |
| FR-W-02 | Dify 与业务数据的边界 | P0 |
| FR-W-03 | **创新点①：三路统一路由（已定案）** | P0 |
| FR-W-04 | **创新点②：算数不交给模型（已定案）** | P0 |
| FR-W-05 | 创新点③：三件式引用（可选，随 FR-Q-03 顺带实现，不作加分主张） | P2 |
| FR-W-06 | **创新点④：Dify 工具节点回连 MES（已定案）** | P0 |
| FR-W-07 | 创新点⑤：质量闭环（可选，随 7.3 评测页顺带实现） | P2 |

**FR-W-01** 在 Dify 中编排「知识问答工作流」：问题改写 → 检索（文档/图谱/工具）→ 重排 → 生成 → 引用格式化；MES 通过 API 调用该工作流，Dify 侧可查看每节点耗时与输入输出。验收：现场打开 Dify 画布演示流程图与运行日志。

**FR-W-02** **Dify 不存储业务数据**：文档正文与数据库内容不落 Dify，Dify 只负责编排与提示词；数据通过 HTTP 工具节点实时回调 MES 只读接口。这条既是架构约束，也是答辩的加分点（说明隐私边界）。

**FR-W-03 创新点①：三路统一路由**（已定案）
文档、图谱、业务数据由同一编排器按问题特征选择，答案里标注使用了哪几路，避免"两个割裂的助手"。

**FR-W-04 创新点②：算数不交给模型**（已定案）
所有聚合（合计、占比、环比）由后端 SQL 计算，模型只表述；沿用阶段1「LLM 不参与算数」的原则并上升为硬约束（FR-A-05），直接对抗大模型算术幻觉。

**FR-W-05 创新点③：三件式引用**（可选）
每条结论可溯源到三种粒度之一：文档（页码/段落）、图谱（实体-关系-实体路径）、数据（表名+主键+查询时间）。该能力由 FR-Q-03、FR-A-08 天然覆盖，实现成本低，作为附带成果记录，不作为加分项主张。

**FR-W-06 创新点④：Dify 工具节点回连 MES**（已定案）
用 Dify 的 HTTP 工具节点调用 MES 只读查询接口，实现"编排平台负责流程、业务系统负责数据与权限"的混合架构，规避把生产数据托管给外部平台。

**FR-W-07 创新点⑤：质量闭环**（可选）
30 题金标集（文档）+ 20 题数据题 + 100 条三元组抽检，形成可重复执行的回归脚本，输出命中率/引用覆盖率/抽取准确率三项指标并留档，作为验收证据。该页由 7.3 评测页承载。

## 5 数据需求

### 5.1 关系库（MySQL 新建）

| 表 | 关键字段 |
| --- | --- |
| `kb_library` | library_id, dept_id, name, type, owner_id, status |
| `kb_library_member` | library_id, user_id, role |
| `kb_document` | doc_id, library_id, dept_id, title, category, current_version, graph_enabled, status |
| `kb_document_version` | version_id, doc_id, version, filename, size, chars, storage_path, active |
| `kb_ingest_task` | task_id, version_id, stage(parse/embed/graph), status, error, started_at, finished_at |
| `kb_chat_session` / `kb_chat_message` | session_id, user_id, dept_id, mode, question, answer, citations(JSON), tool_trace(JSON) |
| `ai_tool_registry`（可配置表） | tool_code, name, schema_json, readonly, permi, enabled |

### 5.2 向量库

- 单集合 + `dept_id`/`library_id` payload 过滤。
- 记录 = 分块：`id, vector, payload{dept_id, library_id, doc_id, version, chunk_index, page, section_label, text}`。
- 按 `doc_id + version` 批量删除，禁止全集合重建。

### 5.3 图模型

- 节点：`Document`、业务实体（附录 B）。
- 边：`MENTIONS`、业务关系（`USED_IN` / `HAS_PROCESS` / `CHECKED_BY` / `MAY_CAUSE` / `REQUIRES`）。
- 约束：`Entity(dept_id, type, name)` 唯一；`Document(doc_id)` 唯一；所有节点带 `dept_id`；建边前校验两端部门一致。

### 5.4 文件存储

原文件落磁盘/MinIO，路径 `dept_id/library_id/version_id/`；库存路径与校验和；删除软删、7 天后清文件。

### 5.5 生命周期

失效版本保留 90 天可回滚；会话引用快照随消息保存，正文按版本快照存，保证删除后引用仍可查看并标注"已删除"。

## 7 验收方式（教师现场操作）

### 7.1 现场验收安排

- **地点**：在开发机（本机）上现场演示，**不依赖教师机器**；Dify、向量库、图库、本地模型全部以 Docker Compose 在本机拉起。
- **形式**：教师在本机**现场操作**，学生只做引导与讲解，不代操作。
- **时长**：8–10 分钟主流程 + 5 分钟自由提问。
- **数据**：使用**项目自带的演示数据**（3 个部门、每部门 5–8 份文档，含检验规范/BOM 说明/工艺说明各 1 份；配套演示工单与库存记录），不读取生产库真实数据。
- **前置检查**：演示前 15 分钟确认 `/mes/ai/status` 五项（本地模型、外部通道、向量库、图库、Dify）为绿，网络断开时本地通道仍可用。
- **通过标准**：主流程全部场景可达，7.3 定量指标在评测页可查。

### 7.2 现场演示脚本（按顺序执行）

| 步骤 | 教师操作 | 期望现象 |
| --- | --- | --- |
| 1 | 以部门 A 账号登录，打开知识库管理 | 只看到 A 部门库；文档列表与处理状态正常 |
| 2 | 上传一份 PDF 规范（或直接用预置文档） | 四阶段进度可见，5 分钟内可检索 |
| 3 | 在对话页选「仅文档(RAG)」，问规范中的事实 | 答案带 `[n]` 引用，点击可跳到原文高亮处 |
| 4 | 问规范里没有的内容 | 明确回答"资料未收录"，不编造 |
| 5 | 切「数据问答(工具)」，问"10 月份某物料库存" | 调用库存工具，回答含数字与表格，末尾有数据来源 |
| 6 | 问一个混合问题（规范要求 + 最近检验结果） | 同时给出文档引用与数据行，标注使用了两路 |
| 7 | 切「图谱(GraphRAG)」并打开图谱页，搜索实体 | 展示节点与关系，可展开邻居；回答中出现图中关联实体 |
| 8 | 打开 Dify，展示编排画布与一次运行日志 | 能看到节点耗时与输入输出 |
| 9 | 换部门 B 账号，重复步骤 3 | 检索不到 A 的文档（隔离生效） |
| 10 | 断掉本地模型，重复步骤 5 | 降级为规则引擎回答并提示，不白屏 |

### 7.3 定量指标（系统内置评测页自证）

| 指标 | 目标 | 度量 |
| --- | --- | --- |
| 文档检索命中率 Recall@5 | ≥ 80% | 30 题金标集 |
| 数据问答正确率 | ≥ 90% | 20 题数据题（答案数值与 SQL 结果一致） |
| 引用覆盖率 | 100% | 抽 30 条答案，事实断言均带引用 |
| 图谱抽取准确率 | ≥ 75% | 抽检 100 条三元组 |
| 越权泄露 | 0 | 7.4 用例 |
| 上传到可检索 | ≤ 5 min（50 页） | 计时 |
| 首字延迟 | ≤ 3s（本地 7B）/ ≤ 1.5s（外部） | 20 次采样 P95 |

### 7.4 越权测试用例（现场可抽做 3 条）

1. 改 `libraryId` 为其他部门；2. 改 `docId` 下载原文；3. 改 `chunkId`；4. 图谱 `nodeId` 跨部门；5. 会话 `sessionId` 跨用户；6. 直接请求文件 URL；7. 检索接口传他人 `deptId`；8. 工具调试接口越权；9. 任务状态越权；10. 库列表枚举。全部期望 403 + 审计记录。

## 附录 A 技术选型建议（非需求）

| 层 | 建议 | 理由 |
| --- | --- | --- |
| 本地对话模型 | Qwen2.5-7B-Instruct Q4_K_M（Ollama / llama.cpp），快档 Qwen2.5-3B-Instruct Q4 | 8 GB 显存下 7B 4bit 可跑（≈4.7 GB），3B 作为延迟敏感场景；vLLM 在 8 GB 卡上 KV cache 余量不足，不推荐 |
| 外部模型 | DeepSeek-chat（已接入） | 工具调用稳定，成本低 |
| 嵌入 | bge-m3（本地 GPU） | 中英混排、长文本表现好 |
| 重排 | bge-reranker-v2-m3 | 显著提升 Top5 命中 |
| 向量库 | Qdrant | 单容器、payload 过滤天然支持部门隔离 |
| 图库 | Neo4j 5.x Community | 任务书点名，生态最全 |
| 编排 | Dify（自托管 Docker） | 必须项，画布可现场演示 |
| 图可视化 | AntV G6 | 力导向布局成熟，与现有前端可集成 |
| 工具调用 | Spring AI 或自研 JSON Schema 校验 | 自研可控性强，便于审计埋点 |

**A.2 退化方案**：无法部署 Qdrant 时用 MySQL 向量列 + 内存余弦；无法部署 Neo4j 时用邻接表 + 递归 CTE；Dify 不可用时降级为自研编排，但需保留可视化流程图（否则创新点失分）。
