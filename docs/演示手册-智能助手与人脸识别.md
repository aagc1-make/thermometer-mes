## 2. 人脸识别演示（约 2 分钟）

### 2.1 一句话原理

摄像头画面**不离开浏览器**：浏览器用人脸模型检测 → 做左右转头活体 → 提 128 维特征 → 只把这串数字发给后端，后端和该账号已存的加密模板算欧氏距离，≤ 0.55 就签发和密码登录相同的令牌。

**边界**：1:1 比对（先输账号再比对该账号的脸），不做“刷脸找人”；活体是浏览器端动作核验，不承诺生产级防伪。

### 2.2 一次性准备：录入人脸

> 只需做一次。换电脑、换浏览器站点地址、管理员重置后要重做。

1. 用 **密码登录** 进入系统（人脸也能登录，但第一次必须先有模板）。
2. 右上角头像 → **个人中心** → 页签 **人脸登录**。
3. 确认状态是“尚未录入人脸”，点 **录入人脸**。
4. 弹窗里：
   - 输入**当前登录密码**；
   - 勾选“我已阅读并同意上述说明，自愿录入人脸特征”；
   - 点 **开始采集**。
5. 允许浏览器使用摄像头（第一次会弹权限框）。采集窗口会**自动开始**，没有“开始”按钮，只有“取消 / 重新识别”。
6. 按屏幕提示做动作，顺序是**固定的**：
   - `请正对镜头，将一张脸放在取景框中央`
   - `请把脸缓缓转向左侧` → `请回正面向镜头`
   - `再请把脸转向右侧` → `请回正面向镜头`
   - `动作已完成，请正对镜头，保持不动`
   - `正在采集特征 1/3 … 3/3`（保持不动）
   - `识别成功`
7. 关掉弹窗，个人中心应显示 **已录入人脸**，并出现“更新人脸 / 追加角度 / 解绑人脸”。

小技巧：光线均匀、正对镜头、摘掉遮挡；戴眼镜或常侧脸的人可再点 **追加角度**（最多 3 个角度，比对时取最近的一个）。

### 2.3 正式演示：人脸登录

1. 右上角 → **退出登录**。
2. 登录页顶部有三个页签：**密码登录 / 验证码登录 / 人脸登录**，点 **人脸登录**。
3. 输入账号 `admin`（只输账号，不输密码）。
4. 点 **开始人脸识别**，弹出标题为“人脸登录”的采集窗口。
5. 重复 2.2 的动作（左转 → 右转 → 采集 3 帧）。
6. 成功后直接进入首页，与密码登录完全一样。

**讲解词**：*“全程照片和视频帧都在浏览器里，服务端只收到 128 个数字；模板是 AES 加密存的，录入和解绑都要再验一次密码。”*

### 2.5 前置条件与配置

| 条件 | 说明 |
| --- | --- |
| 安全上下文 | 必须是 `http://localhost:8095` 或 HTTPS；用局域网 IP + http 访问时摄像头会被浏览器拒绝 |
| 摄像头 | 笔记本内置或外接 USB 均可；被其他程序占用会提示“摄像头被其他程序占用” |
| 模板加密密钥 | 后端必须带 `MES_FACE_TEMPLATE_KEY`（32 字节随机数的 Base64）。**本机已用 `setx` 设到用户环境变量**，新开的 IDEA/终端会自动继承；换密钥等于所有已录模板作废 |
| 模型资源 | `ktg-mes-ui/public/face-api`（约 6.8MB），首次打开采集窗口加载 1–3 秒 |
| 阈值 | 前后端都是 `0.55`（欧氏距离，越小越严）；调大更宽松 |

### 2.6 人脸常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 点录入提示“人脸录入暂不可用，请联系管理员” | 后端没配密钥，或 Qdrant 配了但没起来 | 用带 `MES_FACE_TEMPLATE_KEY` 的方式重启后端；配置了 `MES_FACE_QDRANT_URL` 时确认它在线 |
| 人脸登录提示“人脸登录暂不可用，请使用密码登录” | 同上，服务级不可用 | 同上 |
| 提示“摄像头只能在 HTTPS 或 localhost 下使用” | 用 IP 访问 | 换 `localhost` 或配 HTTPS |
| 提示“没有找到可用的摄像头”/“权限被拒绝” | 没摄像头或浏览器权限被拒 | 检查设备；地址栏权限设置里允许摄像头 |
| 反复“请正对镜头” | 光线太暗、脸太小、戴帽子 | 靠近镜头、补光、摘遮挡 |
| 一直比对失败 | 外观变化大或当初录入质量差 | 个人中心“更新人脸”重录 |
| 首次采集很慢 | 模型首次加载 | 等 1–3 秒；超过 30 秒会提示重试 |

## 3. 智能助手演示（约 6 分钟）

### 3.1 界面地图

| 位置 | 内容 | 用途 |
| --- | --- | --- |
| 顶部菜单 | 智能助手 → 智能问答 / 知识库管理 / 知识图谱 / 问答评测 | 四个功能页 |
| 右上角 | `Dify · 状态` 徽标（未配置/已配置待验证/在线/离线） | 开场先指它，说明本轮是否走 Dify |
| 输入框左下角 | 模式下拉 + 资料范围 | 模式决定走哪条分支，资料范围决定检索哪个库 |
| 回复气泡上方 | `N 步 · X 秒` 灰字 | 点开是轨迹，**演示的核心证据** |
| 轨迹底部 | `Dify 编排 · 运行 <id> · 分支 <分支>` | 与 Dify 控制台对账的钥匙 |

模式下拉共五项：**自动路由 / 仅文档 RAG / 图谱 GraphRAG / 数据问答 / 浏览器资料**。前四项走 Dify，最后一项是浏览器本地资料（不涉及 Dify）。

### 3.2 四题脚本

按顺序问，每问完展开轨迹看一眼再问下一题。

| # | 模式 | 问题 | 应看到 | 讲解点 |
| --- | --- | --- | --- | --- |
| 1 | 图谱 GraphRAG | 红外传感器模块与哪些检验项目有关？ | 轨迹 `图谱检索 · 关联 13 个实体、17 条关系`；气泡里“图谱子图”；引用 4 条 | 图谱分支真的去查了 Neo4j |
| 2 | 仅文档 RAG | 红外传感器模块来料检验有哪些要求？ | `文档检索 · 命中 4 个片段`；引用 4 条可点开原文 | 引用能回到原文分块 |
| 3 | 数据问答 | 工单 MO202610270001 的过程检验结果如何？ | 分支“业务数据”，`无需重排`，表格 1 行 8 列 | 数字由 MES 查库，不经过模型编造 |
| 4 | 自动路由 | 检验规范怎样要求抽检？工单 MO202610270001 的过程检验结果如何？ | 同一条气泡里既有引用又有表格；轨迹出现 `混合问答·文档检索` + `混合问答·业务查询` | 两路检索在**同一个运行编号**里 |

### 3.3 轨迹怎么读

以图谱题为例，点开“N 步”后从上往下：

```
选择资料范围 · MES Demo Library
Dify · 问题改写 · 分支 图谱 · 0 ms
图谱检索 · 关联 13 个实体、17 条关系
Dify · 图谱检索 · 命中 4 个片段 · 2040 ms
Dify · 证据排序 · 图谱关系与文档证据合并排序 · 0 ms
Dify · 回答生成 · 本地模型 → 已授权外部 API → 仅检索 · 0 ms
Dify · 引用整理 · 为证据分配稳定引用编号 · 0 ms
Dify · 完成回执 · 完成回执，交由 MES 展示答案 · 0 ms
Dify 编排 · 运行 648ea19f-0c6d-444b-b059-f305b340730c · 分支 图谱
本地模型生成 / 本地模型完成
```

读法：
- `Dify ·` 开头 = 该阶段由 Dify 节点驱动；括号后的 `X ms` 是这一阶段耗时。
- 没有 `Dify ·` 开头的是 MES 自己的处理（检索细节、模型生成）。
- **最后一条是“结论”**：只有“成功状态 + 运行编号 + 完成回执”三项都通过才会出现 `Dify 编排`；否则会写 `Dify 兜底 · <原因>`。
- 运行编号就是去 Dify 对账的钥匙。

### 3.4 到 Dify 找同一轮

1. 打开 `http://127.0.0.1:8082/app/994568ba-bf12-435e-b021-b4433315b031/logs`（等价于：工作室 → 应用 → **日志与标注**）。
2. 按时间找到刚才那一轮，状态“成功”，点开右侧详情。
3. 依次指出：
   - **输入**只有 `{"ticket": "…", "route": "graph"}`；**输出**只有 `{receipt, route, callback_status}`；
   - **节点链**：领取本轮任务 → 问题改写确认 → 选择检索分支 → 图谱检索 → 汇集阶段凭证 → 证据排序 → 回答生成 → 引用整理 → 完成回执 → 返回执行回执；
   - 点 **选择检索分支**：`actual_value: graph → selected_case_id: case_graph`；
   - 点 **图谱检索**：输出里 `status_code: 200`、`body` 是下一张凭证、`headers` 有 `x-mes-stage / x-mes-next-stage / x-mes-route`；
   - 点 **数据处理**：请求体只有 `POST /mes/ai/dify/callback … {"stage":"graph","ticket":"…"}`。
4. 边界话术：*“Dify 里看不到问题原文、文档片段、库存数字、工单号——它只知道走到哪一步、哪个分支、成功没有；这些数据全在 MES。”*
5. 耗时可互相对照：Dify 节点耗时含 HTTP 往返，MES 轨迹是阶段内部处理，差几十毫秒属正常，量级一致。

### 3.5 问答评测

入口：智能助手 → **问答评测**（仅 admin 可见）。

1. 下拉选 `MES Demo Library`，点 **运行评测**（约 0.5 秒）。
2. 四张卡片应全部 100%：`Recall@5 2/2`、`数值正确率 3/3`、`引用覆盖率 8/8`、`三元组抽检准确率 6/6`。
3. 点任意卡片 → 下方列出样例 → 点一行 → 右侧对照“核对依据 / 实际结果”。
4. 右上 **下载报告** 可导出本次结果。

**关键解读**（务必主动说）：显示 `—` 或“N 项未评测”是**标注缺失被跳过，不是 0 分**。四项分别证明：

| 指标 | 证明什么 |
| --- | --- |
| Recall@5 | 标注文档分块是否被检索进前 5 |
| 数值正确率 | 规则问答的数字与独立 SQL 是否一致 |
| 引用覆盖率 | 引用编号与原文分块是否一一对应 |
| 三元组抽检准确率 | 图谱抽出的 `Item → USED_IN → Product` 与人工标注是否一致 |

**注意**：评测不经过 Dify，评的是 MES 检索与数据口径；Dify 那条链路由运行编号和轨迹证明。两者别混着讲。

### 3.6 退化演示（可选，30 秒）

```powershell
cd E:\dify\docker

```

回 MES 问第 3 题（数据问答）：表格照常出，轨迹末条变成

```
Dify 兜底 · Dify 不可达或等待超时，本轮由 MES 直接执行
```

```powershell

```

### 3.7 助手常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 轨迹里没有任何 `Dify ·`，末条是 `Dify 兜底` | Dify 没起 / nginx 停了 | `docker ps` 看 11 个容器，`docker compose start nginx` |
| 模式选图谱但只有文档引用 | 问题里没有库里存在的实体名 | 问含实体/编码的问题，如“红外传感器模块”“TG-EL-002” |
| 数据问答返回“没有匹配到可用的业务查询” | 问题没命中既有业务规则 | 用“库存/工单/检验/安全库存/流水”等问法 |
| 每问都等十几秒才出答案 | Dify 不可达，在等超时 | 修 Dify，或临时把 `timeout-ms` 调到 3000 再重启后端 |
| 图谱写“没有可用的部门知识库” | 当前账号无可视库 | 用 admin，或把库建到该账号所属部门 |
| 评测三项显示“—” | 缺评测标注文档 | 跑一次评测看“未评测”原因；需要《来料检验规范（问答演示）》《测温枪 BOM 关系演示》两份文档 |

| --- | --- |
| 页面打不开 | 确认后端 8080、前端 8095 在监听；重启前端 `cd ktg-mes-ui; npx vue-cli-service serve --port 8095` |
| 登录一直失败 | 验证码是否算错；账号是否被锁；用 `admin/admin123` |
| 摄像头黑屏 | 关掉其它占用摄像头的程序（会议软件、相机）；重新点开始 |
| 人脸不可用 | 后端缺 `MES_FACE_TEMPLATE_KEY`，按附录 A 的命令重启 |
| Dify 徽标离线 | `cd E:\dify\docker; docker compose up -d`，等 1 分钟再看 |
| 图谱题没有图谱 | Neo4j 没起或 `mes.ai.graph.url` 不是 `http://127.0.0.1:7474`；起服务后重问 |
| 模型回答很慢或退化成片段 | Ollama 没起或缺模型；起 `ollama serve` 后重问 |

## 5. 收尾

1. 演示结束可保留容器与数据，下次直接 `docker compose up -d`。
2. 若演示时导出过报告或截图：把 `ticket`、人脸特征等凭证字段遮盖后再外发。
3. 人脸模板如需清除：个人中心 → 解绑人脸（或管理员在“人脸管理”重置）。

## 附录 A · 启动命令

MySQL（3307）和 Redis（6379）已注册为 Windows 服务（`MySQL80`、`Redis`，自动启动），一般不用手动起；确实要手动时用根目录的 `start-backend.bat`。

```powershell
# 1) 向量库
cd E:\JavaCode\.tools\qdrant; .\qdrant.exe

# 2) 本地模型

$env:OLLAMA_MODELS = 'E:\JavaCode\.tools\ollama\models'
$env:OLLAMA_HOST   = '127.0.0.1:11434'
.\ollama.exe serve

# 3) 图谱（需 JDK21；二进制直启，绕开 neo4j.bat 的 ps1 问题）
cd E:\JavaCode\.tools\neo4j-community-5.26.0
$env:JAVA_HOME = 'C:\Program Files\Java\jdk-21'
& "$env:JAVA_HOME\bin\java.exe" -cp ".\lib\*" -Dbasedir="$PWD" org.neo4j.server.startup.Neo4jCommand console

# 4) Dify（Docker Desktop 需先启动）
cd E:\dify\docker; docker compose up -d
docker compose ps      # 11 个容器 Up 后再继续

# 5) 后端（8080）——具体参数见本机 .tmp-demo/mes-start.md（含密钥，未入库）
cd E:\JavaCode\backend\ktg-mes
java -Dfile.encoding=UTF-8 `
  -Dmes.ai.dify.api-base-url=http://127.0.0.1:8082/v1 `
  -Dmes.ai.dify.api-key=<DIFY 应用密钥> `
  -Dmes.ai.graph.url=http://127.0.0.1:7474 -Dmes.ai.graph.user=neo4j `
  -Dmes.ai.graph.password=<Neo4j 密码> `

  -jar ktg-admin/target/ktg-admin.jar

```

> `MES_FACE_TEMPLATE_KEY` 已用 `setx` 写入用户环境变量，新开的 IDEA/终端会自动继承。
